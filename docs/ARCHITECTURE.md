# Architecture

The webview (TypeScript, xterm.js) draws the terminal and handles everything the user sees. Rust only runs `claude` in a pseudo-terminal (ConPTY on Windows, through `portable-pty`), moves bytes in and out, in a development build records the output of each session to a file (see [Recordings](#recordings)), and owns the project list, whose folders it picks itself (see [Projects](#projects)), with the tabs of each project and the Claude Code session each tab resumes (see [Sessions](#sessions)).

## Bundled ConPTY (Windows)

The Windows build ships Microsoft's ConPTY release next to the executable: `conpty.dll`, `x64/OpenConsole.exe` and its licence as `conpty-LICENSE.txt`, copied from `vendor/conpty/` by `bundle.resources` in `src-tauri/tauri.windows.conf.json` (merged on Windows only, so macOS ships none of them). On Windows, Tauri's resource folder is the executable's folder, in a development build too.

- `portable-pty` loads `conpty.dll` from the executable's folder before the one in Windows, and `conpty.dll` starts `x64/OpenConsole.exe` from its own folder. With the bundled release, the bytes `claude` writes reach xterm.js unchanged; the ConPTY built into Windows rewrites some of them, which breaks composed emojis. `portable-pty` loads it by bare name, so when `conpty.dll` is missing from the executable's folder, Windows looks for it in the current directory and then in each `PATH` folder; only when none has it does `portable-pty` fall back to the ConPTY built into Windows.
- A Rust test (`windows_build_ships_exactly_the_bundled_conpty_files` in `src-tauri/src/lib.rs`) fails when the Windows resources change or a source file is missing. `scripts/check-conpty.ps1`, run by the checks workflow, fails when a file is not signed by Microsoft or its version or SHA-256 differs from the values written in the script. Updating the release is described in `vendor/conpty/README.md`.

## App data folder

Each build has its own app identifier, which names its app data folder and its single-instance lock: a release build keeps `com.cloitre.desktop` from `tauri.conf.json`, a development build (`pnpm tauri dev`, `pnpm tauri build --debug`) uses `com.cloitre.desktop.dev`, set by Rust before Tauri starts. On Windows the folders are `%APPDATA%\com.cloitre.desktop` and `%APPDATA%\com.cloitre.desktop.dev`. A development build also shows `(dev)` after the window title. The identifier is replaced at run time only: the installers `pnpm tauri build --debug` bundles keep `com.cloitre.desktop`, so installing one replaces the installed app. Below, the paths of `projects.json` and `hooks.json` name the release build's folder; recordings exist in a development build only, so their path names the development build's folder.

## How the webview may call Rust

- The app's commands are declared in `src-tauri/build.rs` (`AppManifest::commands`). Tauri then generates an `allow-*` and a `deny-*` permission for each one in `src-tauri/permissions/autogenerated/`.
- Without that declaration, Tauri lets any window with local content call every command registered in `invoke_handler`. With it, a command is refused unless a capability grants its permission to the calling window.
- `src-tauri/capabilities/default.json` grants the commands below to the window labelled `main`, and nothing else. There is no shell permission, no permission to run an arbitrary command, no file system permission and no dialog permission: recordings are only reached through the closed `recording_*` commands, which, but for `recording_enabled`, only a development build registers, and the folder picker is only opened by Rust, inside `project_add` and `project_relocate`, like the confirmation asked when the window closes.
- Besides the app's own commands, the capability grants `core:event:allow-listen` and `core:event:allow-unlisten`, so the webview can listen to the events Rust emits, such as `session-state` (see [Session states](#session-states)); not `core:event:default`, which also lets the webview emit events. It also grants three permissions of the updater plugin, and only these: `updater:allow-check` (ask the update server for a newer version), `updater:allow-download` (download it and check its signature) and `updater:allow-install` (run the downloaded installer). Not `updater:default`, which also grants `allow-download-and-install`. No process plugin: on Windows the installer starts the app again itself. See [Updates](#updates).
- `tauri.conf.json` does not list the capabilities, so Tauri enables every file in `src-tauri/capabilities/`.
- That list is closed: a Rust test (`main_window_gets_exactly_the_closed_list_of_permissions` in `src-tauri/src/lib.rs`) fails when `src-tauri/capabilities/` holds any file other than `default.json`, when that capability has any key other than `$schema`, `identifier`, `description`, `windows` and `permissions` (so no `remote` URLs, no `webviews`, no `platforms`), when a permission is added to or removed from it, when it is granted to any window other than `main`, or when `tauri.conf.json` declares capabilities under `app.security.capabilities` (Tauri v2 accepts inline capabilities there, which would bypass the checks on `src-tauri/capabilities/`). Changing the list means changing the test in the same pull request.

## Commands

Errors reach the webview as a plain message string. Every command runs off the main thread, so a slow pseudo-terminal never freezes the window; calls are not ordered between themselves, so the webview sends each write only after the previous one has resolved.

### `pty_spawn`

Starts `claude` for a tab, in its project's folder, in a new pseudo-terminal.

- **Arguments**: `tabId` (integer from 1 to 4294967295, a tab id returned by `tab_open`), `mode` (string, `"new"` or `"resume"`), `cols` and `rows` (integers from 1 to 65535), `onOutput` (channel), `onExit` (channel).
- **Returns**: the session id (integer, starts at 1, never reused). It numbers the running session for `pty_write`, `pty_resize` and `pty_kill`; it is not the Claude Code session id, which stays in Rust.
- **Streams**: `onOutput` receives the raw output bytes as `ArrayBuffer` chunks, in order. A chunk may end in the middle of a multi-byte character; xterm.js decodes the stream. `onExit` receives the exit code once, when `claude` ends: Rust then closes the pseudo-terminal and sends the exit code only after the last output chunk was sent, or after 2 seconds if the output is still not drained. The two channels are not ordered between themselves on the webview side (a large chunk is fetched later than a small message), so an output chunk can still arrive after the exit code. The session stays registered until `pty_kill`.
- **Modes**, a closed list: any other value of `mode` is refused before the command runs.
  - `"new"`: Rust generates a new session id, deletes any session id the hook left for that tab, stores the new id as the tab's and saves the project file before `claude` starts, then runs `claude --session-id <id> --settings <hooks.json>`.
  - `"resume"`: Rust first applies the session ids the hook left (see [Sessions](#sessions)), then runs `claude --resume <id> --settings <hooks.json>` with the tab's stored session id. When Claude Code no longer has that conversation, `claude` prints "No conversation found with session ID: <id>" and exits with code 1. A resume that exits with a non-zero code within 10 seconds of its start makes the webview say "Claude Code exited with code <N> while resuming. The previous conversation may no longer exist." and offer Resume and New session.
- **What Rust decides alone**: the program is `claude`, and its argument list is exactly one of the two above, built by Rust: `<id>` is a session id Rust generated or checked (36 characters, hexadecimal digits and hyphens at the places of a UUID, stored in lower case, so it never starts with `-` and holds no character `cmd.exe` interprets); `<hooks.json>` is the absolute path of the hook settings file in the app data folder. `--settings <hooks.json>` is left out when that file was not written (see [Sessions](#sessions)). The program is looked up first on the app's `PATH` (on Windows only names with a `PATHEXT` extension count, so the extensionless shell script npm installs is skipped), then at the install locations, in this order, the first existing file winning:
  - Windows: `%USERPROFILE%\.local\bin\claude.exe` (native installer), then `%APPDATA%\npm\claude.cmd` (global npm install);
  - elsewhere: `$HOME/.local/bin/claude`.

  An app started from the desktop may have a `PATH` without the folder of `claude`; the install locations cover that case. A `.cmd` is started directly: Windows runs it through `cmd.exe`, which parses the whole command line. No argument may enter that command line unless Rust has checked its exact form first.
 The working directory is the canonical folder of the tab's project. `TERM=xterm-256color`, `COLORTERM=truecolor` and `CLOITRE_TAB_ID=<tabId>` (in decimal, built by Rust from the integer `tabId`) are added to the inherited environment. The webview cannot pass any folder, argument or environment variable.
- **Records** (development build only): the session to a new file of the recordings folder, starting with its size, then deletes the oldest recording files beyond the kept count (see [Recordings](#recordings)). A file that cannot be created leaves the session unrecorded; the session starts anyway. A file created for a session that then fails to start is deleted.
- **Refuses**: a size of zero columns or rows; a `tabId` of 0 ("the tab id must be at least 1"); a tab id no project holds ("no tab with id <id>"); a project whose folder no longer exists ("the folder of project <name> no longer exists: choose its new location"); a project folder that no longer resolves to a project, compared by canonical path ("the folder is not in the project list"); in mode `"new"`, a read-only project list or a failed save; `claude` found neither on the `PATH` nor at the install locations (the message lists every location tried); a pseudo-terminal that cannot be opened; a start overtaken by a page reload: when every session is stopped at any point after `pty_spawn` starts running (folder check and `claude` lookup included), its process is stopped too and the call fails with "the session was stopped because the page reloaded while it was starting".

### `pty_write`

Sends input to a session.

- **Arguments**: `id` (integer), `data` (string, written as UTF-8).
- **Returns**: nothing.
- **Refuses**: an unknown id; a failed write. Once the process has exited, a write is accepted and does nothing.

### `pty_resize`

Changes the size of a session's terminal.

- **Arguments**: `id` (integer), `cols` and `rows` (integers from 1 to 65535).
- **Returns**: nothing.
- **Records**: the new size, before the pseudo-terminal is resized, and even when that resize fails: the webview has already changed its grid.
- **Refuses**: an unknown id; a size of zero columns or rows; a failed resize. Once the process has exited, a resize is accepted and does nothing.

### `pty_kill`

Stops a session's process, closes its pseudo-terminal and closes its recording. On Windows, the processes the session started are stopped too, even those with their own console. Also used to release a session whose process has already exited.

- **Arguments**: `id` (integer).
- **Returns**: nothing.
- **Refuses**: an unknown id.

When the app exits (see [Closing the window](#closing-the-window)), and whenever the page starts loading (a reload of the webview), every session still registered is stopped and every recording closed. On Windows, the processes of every session are also stopped when the app ends abruptly.

### `recording_enabled`

Tells whether this build records sessions. Registered in every build: the webview asks it once at startup and shows the recording indicator, the marker button and the replay controls only when it answers `true`, and calls no other `recording_*` command otherwise.

- **Arguments**: none.
- **Returns**: `true` in a development build, `false` in a release build.
- **Refuses**: nothing.

### `recording_mark`

The four other `recording_*` commands are registered in a development build only. A release build does not register them, so a call fails as an unknown command; their `allow-*` permissions stay declared and granted, which lets the same capability file serve both builds.

Writes a marker in the recording of a session, to note the moment a display fault is seen. The file is flushed at once.

- **Arguments**: `id` (integer, a session id).
- **Returns**: nothing.
- **Refuses**: a session with no recording (unknown id, released session, or a recording stopped by a write error).

### `recording_current`

Tells whether a session is being recorded.

- **Arguments**: `id` (integer, a session id).
- **Returns**: the file name of its recording, or `null` when it has none or its recording stopped.
- **Refuses**: nothing.

### `recording_list`

Lists the recording files.

- **Arguments**: none.
- **Returns**: an array of `{ name, size }` (file name, size in bytes), newest first: by start time, then by `N`, a name without `N` coming before `-1`. Only files whose name has the form below are listed. A missing folder gives an empty array.
- **Refuses**: a recordings folder that exists but cannot be read.

### `recording_read`

Returns one recording file, for the webview to decode and replay.

- **Arguments**: `name` (string, a file name as returned by `recording_list`).
- **Returns**: the raw bytes of the file, as an `ArrayBuffer`.
- **Refuses**: a name that does not have the exact form below (so no path separator, no `..`, no drive or device name); a name with no regular file in the recordings folder (a folder or a link is refused); a file larger than 64 MiB (67108864 bytes), checked before reading ("recording of <size> bytes exceeds the 67108864-byte limit"); a failed read.

### `project_list`

Lists the projects.

- **Arguments**: none.
- **Returns**: `{ projects, warning, selected }`. `projects` is an array of `{ id, name, path, exists, tabs, activeTab, color, icon }`, in the order the projects were added: `id` (integer), `name` (folder name), `path` (canonical folder path, as last chosen), `exists` (whether that path still names a folder), `tabs` (array of `{ id, title }`, the project's tabs in the order they were opened: `title` is the title the tab's session last set, saved by `tab_set_title`, or `null` when it set none; their session ids are not sent), `activeTab` (the id of the tab to bring to the front: the last active one while it is still one of `tabs`, else the first tab, else `null` when the project has no tab), `color` (the marker color, a color name of `src/marker-catalog.json`, or `null` for no color: the marker then draws its symbol on a dark ground with a border; a stored name the catalog lacks gives the catalog color at position `(id - 1) mod <number of colors>`), `icon` (the marker icon, an icon name of the catalog, or `null` for the initials; a stored name the catalog lacks gives `null`). `color` and `icon` are independent: any color, or none, goes with the initials or with any icon. `warning` is a message string when the project file could not be loaded at startup (see [Projects](#projects)), `null` otherwise; it stays the same until the app restarts. `selected` is the id of the project to select: the last one `project_select` remembered while it is still in the list, else the first project, else `null` when there is no project.
- **Refuses**: nothing.

### `project_add`

Opens the folder picker and adds the chosen folder as a project.

- **Arguments**: none.
- **Returns**: the project, as one entry of `project_list`; the existing project when that folder, under any spelling, is already one; `null` when the user cancels, or at once, without opening a second picker, when a folder picker opened by `project_add` or `project_relocate` is still open.
- **Refuses**: a chosen path that is not valid Unicode; a read-only project list; a failed save.

### `project_relocate`

Opens the folder picker to give a project a new folder, typically one whose folder has moved. The name follows the new folder; the id and tabs are kept.

- **Arguments**: `id` (integer, a project id).
- **Returns**: the updated project, as one entry of `project_list`; `null` when the user cancels, or at once, without opening a second picker, when a folder picker opened by `project_add` or `project_relocate` is still open.
- **Refuses**: an unknown id, before the picker opens; a folder that is already another project's ("the folder is already the folder of project <name>"); a chosen path that is not valid Unicode; a read-only project list; a failed save.

### `project_remove`

Removes a project from the list, with its tabs. Its folder is not touched. A running session of one of its tabs is not stopped. When it was the selected project, the selection moves, in the same save, to the project that takes its place in the list, else to the one before it, else to none.

- **Arguments**: `id` (integer, a project id).
- **Returns**: nothing.
- **Refuses**: an unknown id; a read-only project list; a failed save.

### `project_select`

Remembers a project as the selected one, so that the next run selects it again. Saves nothing when it already is the selected one. On a read-only project list the selection is kept in memory until the app closes.

- **Arguments**: `id` (integer, a project id).
- **Returns**: nothing.
- **Refuses**: an unknown id; a failed save.

### `project_set_marker`

Sets the marker of a project, shown next to it in the list: a color or none, and a symbol, the initials or an icon. The two are independent and both are saved.

- **Arguments**: `id` (integer, a project id), `color` (string, a color name of `src/marker-catalog.json`, or `null` for no color), `icon` (string, an icon name of the catalog, or `null` for the initials).
- **Returns**: the updated project, as one entry of `project_list`.
- **Refuses**: a color or icon the catalog lacks ("no marker color or icon named <name>"); an unknown id; a read-only project list; a failed save.

### `tab_open`

Opens a new tab in a project. Rust gives it a new Claude Code session id, which it keeps; the tab starts no session until `pty_spawn`. The new tab becomes the project's active tab, in the same save.

- **Arguments**: `projectId` (integer, a project id).
- **Returns**: `{ id, title }`: `id` is the tab id (integer, starts at 1, unique across every project, never reused); `title` is `null`.
- **Refuses**: an unknown project id; a read-only project list; a failed save.

### `tab_close`

Closes a tab: it is removed from its project, with the session id the hook left for it. A running session of that tab is not stopped: the webview calls `pty_kill` first. When it was the project's active tab, the active tab moves, in the same save, to the tab that takes its place, else to the one before it, else to none.

- **Arguments**: `tabId` (integer, a tab id).
- **Returns**: nothing.
- **Refuses**: an unknown tab id ("no tab with id <id>"); a read-only project list; a failed save.

### `tab_activate`

Remembers a tab as the active tab of its project, so that the next run brings it to the front again. Saves nothing when it already is the active one. On a read-only project list the active tab is kept in memory until the app closes.

- **Arguments**: `tabId` (integer, a tab id).
- **Returns**: nothing.
- **Refuses**: an unknown tab id ("no tab with id <id>"); a failed save.

### `tab_set_title`

Saves the title a tab's session set in its terminal, so that the next run shows it on the restored tab. Saves nothing when the tab already has that title. The webview strips control characters and cuts the title to 256 characters before sending it, and sends a title once it has stayed unchanged for one second, so a title that changes many times a second is written once.

- **Arguments**: `tabId` (integer, a tab id), `title` (string, at most 256 characters, or `null`; `null` or an empty string clears the title).
- **Returns**: nothing.
- **Refuses**: a title longer than 256 characters or holding a control character ("the tab title must be at most 256 characters, without control characters"); an unknown tab id ("no tab with id <id>"); a read-only project list; a failed save.

## Projects

The project list belongs to Rust: `pty_spawn` runs only in the folder of a project, so a list the webview could write would make that check circular.

- **The folder picker is opened by Rust**, never by the webview: no command takes a folder path to add. The picker runs off the main thread, with the main window as parent.
- **One project per folder**: folders are compared by canonical path, so two spellings of the same folder (`..` segments, links, letter case on Windows) give one project, when adding as when relocating.
- **File**: `projects.json` in the app data folder (on Windows, `%APPDATA%\com.cloitre.desktop\projects.json`). Read once at startup; written after every change.
- **Format, version 2**:

  ```json
  {
    "version": 2,
    "projects": [
      {
        "id": 1,
        "name": "example",
        "path": "C:\\work\\example",
        "tabs": [
          {
            "id": 1,
            "session_id": "0f8e5c1a-3b2d-4c6e-9a7f-1d2c3b4a5e6f",
            "title": "Example task"
          }
        ],
        "active_tab": 1,
        "color": "blue",
        "icon": null
      }
    ],
    "next_id": 2,
    "next_tab_id": 2,
    "selected": 1
  }
  ```

  `id` is unique in the file and never reused, even after the project with the largest id is removed: a new project takes `next_id`, or the largest id plus one when that is higher, and `next_id` becomes its id plus one. `next_id` may be absent (files written before it existed); it then counts as 0. `path` is the canonical folder path. `tabs` lists the project's tabs, in the order they were opened: `id` is at least 1, unique across every project of the file and never reused, by the same rule as project ids with `next_tab_id` (absent from older files, it then counts as 0); `session_id` is the Claude Code session id the tab resumes, in the form `pty_spawn` checks. `title` is the title the tab's session last set (see `tab_set_title`); it is left out when the tab has none, and reads as none when absent or not a string, so files written before it existed keep version 2. `active_tab` is the id of the project's last active tab, or `null`; it may name a tab that is gone, and `project_list` then gives the project's first tab instead. Absent from older files, it counts as `null`. `color` and `icon` are the project's marker, names of `src/marker-catalog.json`, chosen independently. `color` is `null` for no color; `icon` is `null` for the initials. A new project gets the initials and the first catalog color no project shows, or, when every color is shown, the one after the color of the last project that has one. A name the catalog lacks is kept as written: `project_list` then gives the default color, or no icon, without a warning. A `color` that is absent or not a string reads as no color; an `icon` that is absent or not a string reads as the initials. A tab id of 0, a tab id used twice, or a missing or malformed `session_id` makes the whole file unreadable (see below). `selected` is the id of the last selected project, or `null`; it may name a project that is gone, and `project_list` then gives the first project instead. Absent from older files, it counts as `null`. A change of shape that an older app cannot read raises `version`.
- **Version 1** is still read, then saved as version 2 at the next change. It stored the same fields, but an icon replaced the color: a project with a catalog icon showed it on a dark ground. So, on loading, a project with a catalog icon gets `color` `null`; a project without one keeps its `color`, and when that is absent or not a string, gets the catalog color at position `(id - 1) mod <number of colors>`, the one it showed.
- **Writing**: to `projects.json.<process id>.tmp` in the same folder, flushed to disk, then renamed over `projects.json`, so the file is always whole. Only one instance of a build runs, so no other process rewrites the file behind the list in memory: launching the app while it runs brings the running window to the front (shown, restored, focused) and the second process exits before reading the app data folder. The `SessionStart` hook runs the same executable but exits before Tauri starts, so it is not affected. A failed write leaves the file and the list as they were, and the command fails with "the project list could not be saved: <reason>".
- **Unreadable file**: a missing file gives an empty list with no warning. A file that cannot be read, is not valid JSON, has no `version`, a `version` other than 1 or 2, or content that is not a project list, is copied to `projects.json.unreadable` (then `projects.json.unreadable-2`, `-3`… when that name is taken) and the app starts with an empty list; `project_list` returns the warning "The project list could not be loaded (<reason>). It was copied to <copy path> and the app started with an empty list." When the copy fails too, the warning says so and every change is refused with "the project list is read-only until the app restarts: its file could not be loaded nor copied aside", so the file is never overwritten.

## Sessions

Each tab keeps one Claude Code session id, the conversation `"resume"` reopens. Rust generates it (`tab_open`, `pty_spawn` in mode `"new"`) and passes it with `--session-id`, so the conversation has that id from its start. `--resume` keeps the id. `/clear` gives the conversation a new id: Claude Code's `SessionStart` hook tells the app.

- **Hook settings**: at startup Rust writes `hooks.json` in the app data folder (on Windows, `%APPDATA%\com.cloitre.desktop\hooks.json`), passed to every session with `--settings`. Its content is built by Rust; its `SessionStart` entry is, for example:

  ```json
  {"hooks":{"SessionStart":[{"hooks":[{"type":"command","command":"\"C:/Program Files/Cloitre/cloitre.exe\" session-hook"}]}]}}
  ```

  The same file runs the [state hook](#session-states) on the events listed there, with the same command form and `state-hook` instead of `session-hook`.

  The command is the app's own executable, between double quotes with `/` separators, then `session-hook`. Claude Code runs it through a shell (bash when Git Bash is installed, `cmd.exe` otherwise). When that executable path or the path of `hooks.json` holds a character a shell interprets (`"`, `%`, `!`, `^`, `&`, `|`, `<`, `>`, `$`, a backtick, a control character), or the file cannot be written, no hook is written and sessions start without `--settings`: the session id then stays the one Rust gave. The user's own Claude Code hooks keep running beside it.
- **Hook mode**: `cloitre session-hook` runs before Tauri starts and opens no window. It reads at most 1 MiB of the JSON Claude Code sends on its standard input, takes its `session_id`, checked like any session id, and `CLOITRE_TAB_ID` from its environment (inherited from the session, a decimal integer from 1 to 4294967295), then writes the session id to `sessions/<tab id>` in the app data folder, through a temporary file renamed over it. It computes the app data folder the way Tauri does: the platform data folder joined with the app identifier of its own build (see [App data folder](#app-data-folder)), so a development build's hook writes into the development build's folder. Any invalid input writes nothing. It always exits with code 0 and prints nothing, so it never blocks `claude`.
- **When ids are applied**: Rust reads the `sessions` folder at startup and right before every `pty_spawn` in mode `"resume"`. Each file named by a tab id is first renamed to `<tab id>.applying`, so an id the hook writes for that tab meanwhile lands in a new file, left for the next time. A renamed file holding exactly a session id makes that id the tab's session id in the project file, then is deleted. A file that holds anything else, or names no tab, is deleted and ignored; a file whose id could not be saved goes back under its name, unless the hook wrote a newer id there, which then wins. Files not named by a decimal number (the hook's temporary files) are left alone.
- **Limit**: the id is followed at the next resume or the next start of the app, not live: Rust does not watch the folder while a session runs.
- **One instance**: the app never runs twice on the same app data folder, so `hooks.json` and `sessions/` have one owner. A development build is another app with its own folder and lock: it runs beside the installed app, and neither sees the other's projects, tabs or session ids.

## Session states

The app learns live what each tab's session is doing through Claude Code hooks, and tells the webview. Rust only carries the state; the webview decides what to show.

- **Hook events**: `hooks.json` (see [Sessions](#sessions)) runs `"<exe>" state-hook` on these events. The hook reads `hook_event_name` from the JSON on its standard input, `tool_name` for `PreToolUse`, and the number of entries of `background_tasks` (the session's background tasks still in flight) for `Stop` and `SubagentStop`; a `background_tasks` that is absent or not an array counts as empty:

  | Event | State |
  |---|---|
  | `PermissionRequest` | `blocked` |
  | `PreToolUse`, matcher `AskUserQuestion` (and `tool_name` checked again) | `blocked` |
  | `Elicitation` | `blocked` |
  | `UserPromptSubmit` | `prompted` |
  | `PostToolUse`, `PostToolUseFailure`, `ElicitationResult` | `working` |
  | `Stop`, no background task | `done` |
  | `Stop`, background tasks in flight | `background` |
  | `SubagentStop`, no background task | `settled` |
  | `SubagentStop`, background tasks in flight | nothing |
  | `StopFailure` (the turn ended on an API error) | `failed` |

  Any other event, or the same events with an unusable input, sends nothing. The mapping is `state_for` in `src-tauri/src/state.rs`. An event of a subagent carries its `agent_id`; one of the main conversation has none. The hook passes it on as `agent`.
- **Hook mode**: `cloitre state-hook` runs before Tauri starts and opens no window. It reads at most 1 MiB of standard input and `CLOITRE_TAB_ID` (checked as for `session-hook`), sends one message, and exits with code 0, printing nothing, whatever happens. On other systems than Windows it sends nothing.
- **Message**: one JSON line, at most 256 bytes, with two fields and an optional third: `{"tab":3,"state":"blocked"}` for the main conversation, `{"tab":3,"state":"blocked","agent":"a1b2"}` for a subagent. `tab` is the tab id, from 1 to 4294967295; `state` is `blocked`, `prompted`, `working`, `background`, `settled`, `done` or `failed`; `agent` is 1 to 64 ASCII letters, digits, `-` or `_`. An `agent_id` of any other form makes the hook send nothing, and a message with such an `agent` is dropped; `"agent":null` reads as no `agent`. The longest valid message stays well under 256 bytes. A later state is a new `state` value: the channel and the fields stay the same.
- **Channel (Windows)**: a named pipe, `\\.\pipe\<app identifier>.session-state.<user SID>`, for example `\\.\pipe\com.cloitre.desktop.session-state.S-1-5-21-…`. The app identifier keeps a development build and the installed app apart (see [App data folder](#app-data-folder)); the user's SID keeps two accounts of the same machine apart. Rust creates it at startup, on a background thread, and serves one client after another, always keeping one instance waiting.
- **Event**: for every valid message, Rust emits the Tauri event `session-state` to the webview, with the message as payload: `{ "tab": 3, "state": "blocked" }`, plus `"agent"` when the message has one. A message that is too long, is not exactly that object, names a tab id 0, an unknown state or an invalid agent, is dropped without a word. Rust does not check that the tab exists. The webview listens with `listen` from `@tauri-apps/api/event`, which needs `core:event:allow-listen` and `core:event:allow-unlisten` (see [How the webview may call Rust](#how-the-webview-may-call-rust)).
- **What the webview shows** (`src/session-activity.ts`): a tab is blocked while the set of agents that blocked it is not empty, the main conversation counting as one agent. `blocked` adds its agent to the set; `working` and `done` remove their agent only, so a subagent that finishes a tool leaves another one's question on screen; `prompted` empties the set. Input the user types in a blocked tab that holds Enter (pasted text included), is one digit, or is a lone Escape also empties the set: no hook runs between the answer to a permission and the end of the tool, nor after a refusal. An escape sequence, such as an arrow key, does not. A tab works from `prompted`, and on `working` or `background`, until `done` or `failed`. A lone Escape or a lone Ctrl+C typed in a tab interrupts it: Claude Code then sends neither `Stop` nor `StopFailure`, so the webview itself ends the tab's work and empties its set of blocks, without showing done; a tab that only waits for its background tasks is left as it is. `background` leaves it working and waiting for its background tasks: no hook runs when a background shell ends, Claude Code then wakes the session for a turn that ends with another `Stop`, while a background subagent that ends sends `SubagentStop`, hence `settled`. `settled` turns a tab waiting for its background tasks into done, and is ignored for any other tab, such as a foreground subagent ending during a turn. `working` from the main conversation ends the wait for background tasks, since the session is awake again for a turn that ends with `done`; `working` from a subagent does not. `done` and `settled` show done only on a tab not seen; a seen tab shows nothing. Working shows on the seen tab too. `failed` shows an error until the next `prompted` or until the tab is forgotten; seeing the tab does not clear it. Every state but `blocked` ends its agent's block. For a tab and for a project, blocked outranks failed, which outranks done, which outranks working. Working is a light pulse of the dot (a still dot when the system asks for reduced motion), failed a red dot; each state is also named in the tab's and the project's tooltip and accessible name. Known limits, all from a keyboard answer emptying the whole set: Enter between the fields of an MCP elicitation form clears the tab before the form is sent; a digit typed in the free text of an `AskUserQuestion` "Other" answer clears it before the answer is sent; with two subagent permission requests queued, answering the first may clear the tab while the second is on screen. Refusing a permission with a digit or Enter runs no hook and cannot be told apart from approving it, so the tab keeps working until the next `prompted` or `done`. Ctrl+C at an empty prompt also counts as an interrupt, which is harmless: the tab had no work.
- **Never blocking `claude`**: the hook does not wait for the app. When the pipe does not exist (the app is not running) it gives up at once; when every instance is busy it waits for one at most 100 ms, then tries once more. Any error ends the hook with code 0.
- **Security**:
  - The pipe's security descriptor is built by Rust: its owner is the current user, and its protected DACL holds one entry, every access for the current user's SID. No other account can open it, write to it or add an instance to it.
  - Every instance is created with `PIPE_REJECT_REMOTE_CLIENTS`: no client from another machine.
  - The first instance is created with `FILE_FLAG_FIRST_PIPE_INSTANCE`: when a pipe of that name already exists, created by any process, the app does not join it; it runs without session states.
  - Before writing, the hook asks the pipe for its server process (`GetNamedPipeServerProcessId`) and compares the user SID of that process's token with its own. When they differ, or cannot be read, it sends nothing: a pipe another account created first under that name gets no message. The hook connects with `SECURITY_ANONYMOUS`, so the server cannot impersonate it.
  - Rust tests (`src-tauri/src/state/windows.rs`) check the DACL of a created pipe, the pipe flags, the refusal of an existing pipe, the SID comparison and a round trip from client to server.

## Closing the window

When the main window is asked to close, Rust counts the sessions whose process still runs. With none, the window closes at once. Otherwise the close is held and a native dialog, opened by Rust with the window as parent and without blocking the main thread, asks "1 session running. Close anyway?" or "<N> sessions running. Close anyway?", with the buttons Close and Cancel. Close lets the app exit, which stops every session; Cancel leaves everything running. The webview gets no dialog permission for this.

`claude` processes do not survive the app: every session is stopped when it exits. Reopening a tab offers `"resume"` or `"new"`.

## Updates

A release build looks for a newer version once, at startup, through the updater plugin (`tauri-plugin-updater`). A development build (`pnpm tauri dev`, `pnpm tauri build --debug`) never does: Rust registers the plugin only when `debug_assertions` is off (`CHECKS_FOR_UPDATES` in `src-tauri/src/lib.rs`), so the webview's check is refused and shows nothing.

- **Where**: `plugins.updater.endpoints` in `tauri.conf.json` names `https://github.com/AxiaCoder/cloitre/releases/latest/download/latest.json`, the `latest.json` of the latest published release. A draft is not seen.
- **Signature**: every installer is signed with the maintainer's key at release time (see `docs/RELEASING.md`); the public key is `plugins.updater.pubkey` in `tauri.conf.json`. Only the release build makes the signed update files: `release.yml` merges `src-tauri/tauri.release.conf.json`, which sets `bundle.createUpdaterArtifacts`, so a local build needs no private key. The plugin refuses a file whose signature is missing or does not match, and nothing is installed.
- **Consent**: the startup check downloads nothing. A newer version shows a notice in the rail; a failed check shows nothing. Every install attempt, Try again included, asks first, saying how many sessions run at that moment and will stop; Cancel changes nothing.
- **Order**: the update downloads while the sessions keep running. Then the webview stops every session through `pty_kill`, and only then asks the plugin to install. On Windows the plugin starts the NSIS installer and exits the app without asking the window to close, so the confirmation of [Closing the window](#closing-the-window) is not shown; the installer starts the app again. The tabs come back, each offering `"resume"` or `"new"`.
- **Failure**: a download or a signature that fails leaves the sessions running and shows why, with Try again. An installer that fails to start comes after the sessions were stopped: the tabs that ran one show as ended, each offering `"resume"` or `"new"`.

## Recordings

In a development build (`pnpm tauri dev`, or `pnpm tauri build --debug`), every session is recorded, so a display fault can be replayed in xterm.js without any pseudo-terminal: wrong again on replay points at xterm.js, right on replay points at the pseudo-terminal.

- **Release build**: nothing is recorded, the `recordings` folder is never created, no `recording_*` command but `recording_enabled` is registered, and the webview, told so by `recording_enabled`, hides the recording indicator, the marker button and the replay controls and never calls those commands.
- **Folder**: `recordings` in the app data folder (on Windows, `%APPDATA%\com.cloitre.desktop.dev\recordings`), never in the repository.
- **File name**: the UTC start time, `YYYYMMDD-HHMMSS.rec`; `YYYYMMDD-HHMMSS-N.rec` when a file with that name already exists.
- **Retention**: each new recording keeps the 20 newest files of the folder, the new one included, in the order `recording_list` gives, and deletes the older ones. Only files with a recording name are touched, and never the file of a running session: one spared that way leaves more than 20 files, without deleting a newer one instead. A file that cannot be deleted stays; the session starts anyway.
- **Format**: a sequence of records, nothing before the first. Integers are little-endian.

  | Field | Type | Meaning |
  |---|---|---|
  | time | `u64` | milliseconds since the session started |
  | type | `u8` | `1` output, `2` size, `3` marker |
  | length | `u32` | size of the data, in bytes |
  | data | `length` bytes | see below |

  - **Output** (`1`): the bytes exactly as read from the pseudo-terminal, one record per read, so a record may end in the middle of a multi-byte character.
  - **Size** (`2`): 4 bytes, columns then rows, each a `u16`. The first record of every file is the size the session started with; each `pty_resize` with a valid size adds one, written before the pseudo-terminal is resized.
  - **Marker** (`3`): no data. Written by `recording_mark`.
- **Writing**: buffered (64 KiB), written out when the buffer is full, when a record arrives and the last write-out is at least 500 ms old, at each marker and when the recording closes. Nothing is written out between records: after a quiet spell the buffer can hold output of any age. A crash loses everything still buffered, not only the last record; a marker (`recording_mark`, F9) writes it out at once. The first write error stops the recording for good; the session goes on. A file cut short by a crash may end in the middle of a record: the webview drops that record and says so.
- **Replay** (webview only): a replay opens its own read-only tab, with no session, in the selected project; no session is stopped. Its screen is reset and its grid no longer follows the window. Output records are written to xterm.js one by one, in their recorded split; each size record is applied to the terminal once the earlier output has been processed. Speeds: instant, or real time with the recorded delays. *Next mark* replays instantly up to the next marker and pauses there. Loading a replay and stopping a replay take turns: each waits for the one before it and ends the replay on screen first. Ending a replay clears the screen and lets the grid follow the window again.
  - **Limits of the verdict.** A size record is written when `pty_resize` arrives, but output chunks already read from the pseudo-terminal and still on their way to the webview were drawn live at the new size, while the replay draws them at the old one. A defect that shows in the first output after a resize and not in the replay is not proof that the pseudo-terminal is at fault. The renderer and the Unicode version are not recorded: replay with the same settings as the live session. A replay draws at the recorded size; a window smaller than that size crops the grid, so replay in a window at least as large.
