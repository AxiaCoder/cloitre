# Architecture

The webview (TypeScript, xterm.js) draws the terminal and handles everything the user sees. Rust only runs `claude` in a pseudo-terminal (ConPTY on Windows, through `portable-pty`), moves bytes in and out, records the output of each session to a file (see [Recordings](#recordings)), and owns the project list, whose folders it picks itself (see [Projects](#projects)).

## How the webview may call Rust

- The app's commands are declared in `src-tauri/build.rs` (`AppManifest::commands`). Tauri then generates an `allow-*` and a `deny-*` permission for each one in `src-tauri/permissions/autogenerated/`.
- Without that declaration, Tauri lets any window with local content call every command registered in `invoke_handler`. With it, a command is refused unless a capability grants its permission to the calling window.
- `src-tauri/capabilities/default.json` grants the commands below to the window labelled `main`, and nothing else. There is no shell permission, no permission to run an arbitrary command, no file system permission and no dialog permission: recordings are only reached through the closed `recording_*` commands, and the folder picker is only opened by Rust, inside `project_add` and `project_relocate`.
- `tauri.conf.json` does not list the capabilities, so Tauri enables every file in `src-tauri/capabilities/`.
- That list is closed: a Rust test (`main_window_gets_exactly_the_closed_list_of_permissions` in `src-tauri/src/lib.rs`) fails when `src-tauri/capabilities/` holds any file other than `default.json`, when that capability has any key other than `$schema`, `identifier`, `description`, `windows` and `permissions` (so no `remote` URLs, no `webviews`, no `platforms`), when a permission is added to or removed from it, when it is granted to any window other than `main`, or when `tauri.conf.json` declares capabilities under `app.security.capabilities` (Tauri v2 accepts inline capabilities there, which would bypass the checks on `src-tauri/capabilities/`). Changing the list means changing the test in the same pull request.

## Commands

Errors reach the webview as a plain message string. Every command runs off the main thread, so a slow pseudo-terminal never freezes the window; calls are not ordered between themselves, so the webview sends each write only after the previous one has resolved.

### `pty_spawn`

Starts `claude` in a folder, in a new pseudo-terminal.

- **Arguments**: `folder` (string, absolute path of a project folder), `cols` and `rows` (integers from 1 to 65535), `onOutput` (channel), `onExit` (channel).
- **Returns**: the session id (integer, starts at 1, never reused).
- **Streams**: `onOutput` receives the raw output bytes as `ArrayBuffer` chunks, in order. A chunk may end in the middle of a multi-byte character; xterm.js decodes the stream. `onExit` receives the exit code once, when `claude` ends: Rust then closes the pseudo-terminal and sends the exit code only after the last output chunk was sent, or after 2 seconds if the output is still not drained. The two channels are not ordered between themselves on the webview side (a large chunk is fetched later than a small message), so an output chunk can still arrive after the exit code. The session stays registered until `pty_kill`.
- **What Rust decides alone**: the program is `claude`, with no argument. It is looked up first on the app's `PATH` (on Windows only names with a `PATHEXT` extension count, so the extensionless shell script npm installs is skipped), then at the install locations, in this order, the first existing file winning:
  - Windows: `%USERPROFILE%\.local\bin\claude.exe` (native installer), then `%APPDATA%\npm\claude.cmd` (global npm install);
  - elsewhere: `$HOME/.local/bin/claude`.

  An app started from the desktop may have a `PATH` without the folder of `claude`; the install locations cover that case. A `.cmd` is started directly: Windows runs it through `cmd.exe`, which parses the whole command line. No argument coming from the webview may enter that command line unless Rust has checked its exact form first.
 The working directory is the canonical form of `folder`. `TERM=xterm-256color` and `COLORTERM=truecolor` are added to the inherited environment. The webview cannot pass any argument or environment variable.
- **Records**: the session to a new file of the recordings folder, starting with its size. A file that cannot be created leaves the session unrecorded; the session starts anyway. A file created for a session that then fails to start is deleted.
- **Refuses**: the stored path of a project whose folder no longer exists ("the folder of project <name> no longer exists: choose its new location"); a relative folder path; a folder that does not exist; a path that is not a directory; a folder that is not the folder of a project, compared by canonical path ("the folder is not in the project list"); a size of zero columns or rows; `claude` found neither on the `PATH` nor at the install locations (the message lists every location tried); a pseudo-terminal that cannot be opened; a start overtaken by a page reload: when every session is stopped at any point after `pty_spawn` starts running (folder check and `claude` lookup included), its process is stopped too and the call fails with "the session was stopped because the page reloaded while it was starting".

### `pty_write`

Sends input to a session.

- **Arguments**: `id` (integer), `data` (string, written as UTF-8).
- **Returns**: nothing.
- **Refuses**: an unknown id; a failed write. Once the process has exited, a write is accepted and does nothing.

### `pty_resize`

Changes the size of a session's terminal.

- **Arguments**: `id` (integer), `cols` and `rows` (integers from 1 to 65535).
- **Returns**: nothing.
- **Records**: the new size, before the pseudo-terminal is resized, and even when that resize fails: the webview has already changed its grid.
- **Refuses**: an unknown id; a size of zero columns or rows; a failed resize. Once the process has exited, a resize is accepted and does nothing.

### `pty_kill`

Stops a session's process, closes its pseudo-terminal and closes its recording. On Windows, the processes the session started are stopped too, even those with their own console. Also used to release a session whose process has already exited.

- **Arguments**: `id` (integer).
- **Returns**: nothing.
- **Refuses**: an unknown id.

When the app exits, and whenever the page starts loading (a reload of the webview), every session still registered is stopped and every recording closed. On Windows, the processes of every session are also stopped when the app ends abruptly.

### `recording_mark`

Writes a marker in the recording of a session, to note the moment a display fault is seen. The file is flushed at once.

- **Arguments**: `id` (integer, a session id).
- **Returns**: nothing.
- **Refuses**: a session with no recording (unknown id, released session, or a recording stopped by a write error).

### `recording_current`

Tells whether a session is being recorded.

- **Arguments**: `id` (integer, a session id).
- **Returns**: the file name of its recording, or `null` when it has none or its recording stopped.
- **Refuses**: nothing.

### `recording_list`

Lists the recording files.

- **Arguments**: none.
- **Returns**: an array of `{ name, size }` (file name, size in bytes), newest first. Only files whose name has the form below are listed. A missing folder gives an empty array.
- **Refuses**: a recordings folder that exists but cannot be read.

### `recording_read`

Returns one recording file, for the webview to decode and replay.

- **Arguments**: `name` (string, a file name as returned by `recording_list`).
- **Returns**: the raw bytes of the file, as an `ArrayBuffer`.
- **Refuses**: a name that does not have the exact form below (so no path separator, no `..`, no drive or device name); a name with no regular file in the recordings folder (a folder or a link is refused); a failed read.

### `project_list`

Lists the projects.

- **Arguments**: none.
- **Returns**: `{ projects, warning }`. `projects` is an array of `{ id, name, path, exists }`, in the order the projects were added: `id` (integer), `name` (folder name), `path` (canonical folder path, as last chosen), `exists` (whether that path still names a folder). `warning` is a message string when the project file could not be loaded at startup (see [Projects](#projects)), `null` otherwise; it stays the same until the app restarts.
- **Refuses**: nothing.

### `project_add`

Opens the folder picker and adds the chosen folder as a project.

- **Arguments**: none.
- **Returns**: the project, as one entry of `project_list`; the existing project when that folder, under any spelling, is already one; `null` when the user cancels.
- **Refuses**: a chosen path that is not valid Unicode; a read-only project list; a failed save.

### `project_relocate`

Opens the folder picker to give a project a new folder, typically one whose folder has moved. The name follows the new folder; the id and tabs are kept.

- **Arguments**: `id` (integer, a project id).
- **Returns**: the updated project, as one entry of `project_list`, or `null` when the user cancels.
- **Refuses**: an unknown id, before the picker opens; a folder that is already another project's ("the folder is already the folder of project <name>"); a chosen path that is not valid Unicode; a read-only project list; a failed save.

### `project_remove`

Removes a project from the list. Its folder is not touched.

- **Arguments**: `id` (integer, a project id).
- **Returns**: nothing.
- **Refuses**: an unknown id; a read-only project list; a failed save.

## Projects

The project list belongs to Rust: `pty_spawn` runs only in the folder of a project, so a list the webview could write would make that check circular.

- **The folder picker is opened by Rust**, never by the webview: no command takes a folder path to add. The picker runs off the main thread, with the main window as parent.
- **One project per folder**: folders are compared by canonical path, so two spellings of the same folder (`..` segments, links, letter case on Windows) give one project, when adding as when relocating.
- **File**: `projects.json` in the app data folder (on Windows, `%APPDATA%\com.cloitre.desktop\projects.json`). Read once at startup; written after every change.
- **Format, version 1**:

  ```json
  {
    "version": 1,
    "projects": [
      { "id": 1, "name": "example", "path": "C:\\work\\example", "tabs": [] }
    ],
    "next_id": 2
  }
  ```

  `id` is unique in the file and never reused, even after the project with the largest id is removed: a new project takes `next_id`, or the largest id plus one when that is higher, and `next_id` becomes its id plus one. `next_id` may be absent (files written before it existed); it then counts as 0, so the format version stays 1. `path` is the canonical folder path. `tabs` is kept for the tab and session issues; its entries are not defined yet. A change of shape that an older app cannot read raises `version`.
- **Writing**: to `projects.json.<process id>.tmp` in the same folder, flushed to disk, then renamed over `projects.json`, so the file is always whole. Two app instances each keep their own list in memory: one can overwrite a change of the other, never break the file. A failed write leaves the file and the list as they were, and the command fails with "the project list could not be saved: <reason>".
- **Unreadable file**: a missing file gives an empty list with no warning. A file that cannot be read, is not valid JSON, has no `version`, another `version`, or content that is not a project list, is copied to `projects.json.unreadable` (then `projects.json.unreadable-2`, `-3`… when that name is taken) and the app starts with an empty list; `project_list` returns the warning "The project list could not be loaded (<reason>). It was copied to <copy path> and the app started with an empty list." When the copy fails too, the warning says so and every change is refused with "the project list is read-only until the app restarts: its file could not be loaded nor copied aside", so the file is never overwritten.

## Recordings

Every session is recorded, so a display fault can be replayed in xterm.js without any pseudo-terminal: wrong again on replay points at xterm.js, right on replay points at the pseudo-terminal.

- **Folder**: `recordings` in the app data folder (on Windows, `%APPDATA%\com.cloitre.desktop\recordings`), never in the repository.
- **File name**: the UTC start time, `YYYYMMDD-HHMMSS.rec`; `YYYYMMDD-HHMMSS-N.rec` when a file with that name already exists.
- **Format**: a sequence of records, nothing before the first. Integers are little-endian.

  | Field | Type | Meaning |
  |---|---|---|
  | time | `u64` | milliseconds since the session started |
  | type | `u8` | `1` output, `2` size, `3` marker |
  | length | `u32` | size of the data, in bytes |
  | data | `length` bytes | see below |

  - **Output** (`1`): the bytes exactly as read from the pseudo-terminal, one record per read, so a record may end in the middle of a multi-byte character.
  - **Size** (`2`): 4 bytes, columns then rows, each a `u16`. The first record of every file is the size the session started with; each `pty_resize` with a valid size adds one, written before the pseudo-terminal is resized.
  - **Marker** (`3`): no data. Written by `recording_mark`.
- **Writing**: buffered (64 KiB), written out when the buffer is full, when a record arrives and the last write-out is at least 500 ms old, at each marker and when the recording closes. Nothing is written out between records: after a quiet spell the buffer can hold output of any age. A crash loses everything still buffered, not only the last record; a marker (`recording_mark`, F9) writes it out at once. The first write error stops the recording for good; the session goes on. A file cut short by a crash may end in the middle of a record: the webview drops that record and says so.
- **Replay** (webview only): the session is stopped first, the screen reset and the grid no longer follows the window. Output records are written to xterm.js one by one, in their recorded split; each size record is applied to the terminal once the earlier output has been processed. Speeds: instant, or real time with the recorded delays. *Next mark* replays instantly up to the next marker and pauses there. Loading a replay, starting a session and stopping a replay take turns: each waits for the one before it and ends the replay on screen first. Ending a replay clears the screen and lets the grid follow the window again.
  - **Limits of the verdict.** A size record is written when `pty_resize` arrives, but output chunks already read from the pseudo-terminal and still on their way to the webview were drawn live at the new size, while the replay draws them at the old one. A defect that shows in the first output after a resize and not in the replay is not proof that the pseudo-terminal is at fault. The renderer and the Unicode version are not recorded: replay with the same settings as the live session. A replay draws at the recorded size; a window smaller than that size crops the grid, so replay in a window at least as large.
